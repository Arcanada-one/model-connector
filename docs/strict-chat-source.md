Status: default-disabled additive source, not account entitlement, production

The optional `STRICT_CHAT_BOUNDARY` token is deliberately not registered in any
module. With no trusted composition both new handlers refuse. A qualified
incumbent may supply `StrictChatService` only after independently binding the
existing authenticated API identity, current policy, grant/cap/account/rate-card,
source/config/deployment pins, exact encoder, provider hard output enforcement,
restricted store and all-writer/revoker fence. No source callback or possession
of an interface supplies those qualifications. No credentials are loaded here.

POST `/connectors/:name/chat/completions` accepts only explicit `deepseek` and the
closed `mc-chat/v1` DTO: ordered text conversation, typed functions, complete
protected continuation, model/capability/admission/rate/checkpoint pins, immutable
intent/attempt/generation and bounded deadline/input/output. Parallel tools,
unknown fields, unresolved tool responses and unsupported modality are refused.
The original authority verifier must validate each thinking/effort/model feature
against the actual capability pin. Requested bounds are not authentic capacity.

The trusted transport supplies exactly one physical `SingleSend` using existing
isolated credentials. Its implementation must disable redirects, retry,
reconnection, output repair and fallback. `DeepSeekStrictStream` invokes that
port once and validates genuine incremental SSE/UTF-8/tool fragments, served
model, termination, usage and byte bounds. Protected deltas are forwarded only
to the current isolated caller. No generic replay or prompt/reasoning log exists.
A supplied transport that secretly retries is not qualified by these unit tests.

`SqlStrictIntentStore` uses an incumbent restricted connection, creates no pool,
performs no migrations and inserts durable `dispatch_started` before egress.
Tenant/intent uniqueness plus full request digest prevents concurrent duplicates
and restart redispatch; no timeout/429/released-customer-hold exception exists.
The separate supplier table retains exact unit/scale and authentic reference
pins, independently of legacy customer credit. It does not itself mint or check
a financial grant: the supplied authentic verifier reserves/checks cumulative
capacity under its original shared fence. Missing that backend means refusal.
There is no automatic release, reset, expiration sweep or replay response body.

Only a committed safe receipt with actual terminal usage yields successful DONE.
Missing usage, cancellation, truncation, body drift or settlement failure retains
pending/uncertain supplier exposure; a lost final ACK is reconciled through the
current-policy and tenant scoped GET `/connectors/intents/:intentId`. Status never
redispatches or returns protected continuation. SQL source tests are not actual
PostgreSQL commit/permission tests. Deployment of the migration and authenticated
backend/fence qualification remain separately owned and unperformed.
